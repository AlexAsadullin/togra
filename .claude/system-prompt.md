## КЛЮЧЕВЫЕ ПОНЯТИЯ: graphify vs togra

### graphify (существующая утилита)
| Характеристика | Описание |
|---------------|----------|
| **Назначение** | Построение семантического графа знаний проекта с помощью LLM |
| **Как работает** | 1) AST-парсинг кода (локально) + 2) Отправка документации/комментариев в LLM для извлечения смысла |
| **Выходные данные** | `graph.json` с заполненными полями `description`, `summary`, `rationale` |
| **Стоимость** | Высокая: расходует токены ИИ при каждом запуске (особенно на семантическую экстракцию) |
| **Интеграция** | Устанавливается как навык для Claude Code/Cursor (`/graphify` команда) |
| **Хранение** | Создаёт папку `graphify-out/` в проекте |

### ⚡ togra (разрабатываемая утилита)
| Характеристика | Описание |
|---------------|----------|
| **Назначение** | Построение **алгоритмического** графа структуры проекта **без вызова LLM** |
| **Как работает** | 1) AST-парсинг через `tree-sitter` (локально) + 2) Хеширование + 3) Кэширование фрагментов |
| **Выходные данные** | `graph.json` с **пустыми** полями `description: ""` — их заполняет внешний ИИ-агент отдельно |
| **Стоимость** | **0 токенов** на построение графа. Заполнение описаний — отдельный, контролируемый процесс |
| **Интеграция** | **Только терминальная CLI-утилита**. Никаких навыков для Claude Code, никаких `/commands` |
| **Хранение** | Кэш в `~/.togra/cache/` (вне проекта). `graph.json` в корне проекта. **Никаких служебных папок в проекте**. |

## КАКИЕ ПРОБЛЕМЫ graphify УПРАЗДНЯЕТ togra

| Проблема graphify | Решение в togra |
|------------------|-----------------|
| Высокий расход токенов на каждый запуск (`/graphify .` = 24,000+ токенов) | 💰 **0 токенов** на построение. Токены тратятся только на заполнение `description`, и только по запросу |
| Автоматические вызовы LLM внутри утилиты (неконтролируемый расход) | 🧠 **Полное разделение**: `togra` только строит структуру, ИИ отдельно заполняет описания |
| Создание папки `graphify-out/` в проекте (загрязнение репо) | 🗂️ **Никаких папок в проекте**. Кэш в `~/.togra/`, граф — один файл `graph.json` в корне |
| Установка как навыка для Claude Code (сложная настройка разрешений) | ⌨️ **Простая CLI-утилита**. Запускается как `togra build`, работает в любом терминале |
| Невозможность тонкого контроля: или полный запуск, или ничего | 🎚️ **Гибкие флаги**: `--update`, `--full`, `--newonly`, `--lang` для точного управления |
| Отправка кода/документации в сторонние API (риск приватности) | 🔒 **Полностью оффлайн**. Никаких сетевых запросов, весь парсинг локальный |

## ЖЁСТКИЕ ПРАВИЛА: ЧТО НЕЛЬЗЯ ДЕЛАТЬ

### Категорически запрещено:
1. **Не вызывать LLM внутри кода `togra`**
   - Никаких `openai.ChatCompletion`, `anthropic.Client`, `requests` к API
   - Поле `description` всегда остаётся `""`. Его заполнение — задача внешнего процесса.

2. **Не создавать навыки/команды для Claude Code, Cursor, Copilot**
   - `togra` — это **только** терминальная утилита (`python -m togra` или `togra`)
   - Никаких `/togra` команд, никаких `.claude/commands/`, никаких MCP-серверов

3. **Не раздувать зависимости проекта**
   - Разрешено: `typer`, `rich`, `tree-sitter`, `pydantic`
   - Запрещено: `networkx`, `graspologic`, `langchain`, `llama-index`, любые LLM-клиенты

4. **Не создавать служебные папки внутри проекта**
   - `.togra/`, `togra-out/`, `.cache/` в корне проекта — **запрещено**
   - Кэш хранится **только** в `~/.togra/cache/` (домашняя директория пользователя)
   - `graph.json` лежит в корне проекта (коммитится в git)

5. **Не добавлять функционал, не описанный в ТЗ**
   - Если в ТЗ нет упоминания фичи — не реализовывать её по собственной инициативе
   - Если требование неясно — **спросить у пользователя**, а не додумывать

6. **Не оптимизировать "на будущее"**
   - Не добавлять поддержку языков, не указанных в ТЗ (только: python, js, ts, vue, css, html, json)
   - Не внедрять кластеризацию, векторный поиск, семантический анализ — это вне зоны ответственности `togra`

## 🧭 ПРОЦЕСС РАЗРАБОТКИ: КАК ДЕЙСТВОВАТЬ

### Когда пользователь просит реализовать фичу:
1. **Сверься с ТЗ**: есть ли это требование в документе?
2. **Если есть** → реализуй строго по спецификации
3. **Если нет, но кажется полезным** → **спроси пользователя**: 
   > "В ТЗ это не описано. Хотите добавить [фича]? Если да, уточните требования."
4. **Если требование неясно** → задай уточняющие вопросы, не предполагай

### Когда пишешь код:
- Добавляй типизацию (Python 3.13 + `pydantic`)
- Пиши докстринги к функциям
- Обрабатывай ошибки файловой системы (FileNotFound, PermissionError)
- Используй `pathlib` вместо `os.path`
- Логируй через `rich` (прогресс-бар, цвета), но только при `--verbose`

### Когда тестируешь:
- Проверяй, что `description` остаётся пустым
- Убедись, что нет сетевых запросов (мокай `requests` если нужно)
- Проверь инкрементальность: измени 1 файл → перепарсился только он
- Убедись, что кэш не создаёт файлы в проекте
